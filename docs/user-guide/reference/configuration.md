# Configuration

!!! tip "In short"
    Put the settings you change in `~/.config/histmersion/histmersion.conf`, under `histmersion { … }`,
    and run `histmersion config reload`. `histmersion config path` says where the file is;
    `histmersion about` says which file the running server read. An environment variable of the
    service wins over the file.

Everything runtime-tunable is in
[`modules/core/src/main/resources/reference.conf`](https://github.com/histmersion/histmersion/blob/master/modules/core/jvm/src/main/resources/reference.conf).
Nothing is hardcoded anywhere else — a test greps `src/main` for literal ports and fails the build if
one reappears. Most keys take an env override (the table below).

**The config file.** Settings you change go in `histmersion.conf`, with the same keys as
`reference.conf` under `histmersion { … }` — only the ones you change:

```hocon
histmersion {
  converter.parallelism = 2
  agents.step.max-tokens = 8192
}
```

It is `$HISTMERSION_CONFIG` when that is set, else `$XDG_CONFIG_HOME/histmersion/histmersion.conf`
(default `~/.config/histmersion/histmersion.conf`) on macOS and Linux alike — with your other
settings, not in the server-owned data directory, which never moves it.

Precedence, highest first: **environment variable > `histmersion.conf` > `reference.conf`**. An env var
beats the file even for a key the file sets — so a setting in the LaunchAgent's `EnvironmentVariables`
(or the Linux service's `Environment=`) wins over the file; remove it there to manage the setting in the
file. Only the environment can move the file (nothing inside it does). The file is read at startup
and again on `histmersion config reload` (below): no restart after editing. A missing file is fine; a
file that does not parse, or a value of the wrong type, stops the server (exit 3) with the file and the
key in the log (and makes a reload change nothing); a key that is no
setting (a typo such as `agents.step.max-token`) is logged as a warning and ignored. `histmersion about`
(and the web UI's About window) says which file the running server read and lists ignored keys;
`histmersion config path` prints the location on this machine and checks the file. The CLI reads the
same file (`cli.server-url`, `cli.calibre.*`). The installers write a commented template, with no
settings, when there is no file, and never touch an existing one.

## Reloading the config (no restart)

`histmersion config reload` (REST `POST /api/config/reload`, the MCP `config` tool with
`action: "reload"`) makes the running server read its config file again and switch to it in place —
the database included. The server's components form a graph (pool → migrations → read-only pool,
agent lease; plugins → acquisition clients; the file watcher): a reload rebuilds the ones whose keys
changed and everything that depends on them, **beside** the running ones, and switches over only when
all of them built. So a reload that names a database that is not there, a file that does not parse or a
mistyped value changes **nothing**, and says why.

- **The database.** A changed `db.*` opens a pool on the new database, migrates it, provisions the
  read-only role there, claims the agent lease there (giving it up on the old one) and fails the new
  database's interrupted jobs, as a start does. Work that started before the switch — a request, an OCR
  job, an agent run, a background job — finishes on the database it started on; new work goes to the new
  one. The old pool closes when its last user lets go; the reload waits `config.drain-seconds` for that
  and then reports what is still draining (it keeps draining; nothing is cut off).
- **Plugins.** Only the plugins whose `plugins.<id>` block changed are registered again — all of them
  when `plugins.order` or a secret vault's block changed, and all but the built-in media collections and
  event catalogues when `acquire.*` changed (those read their `media.*`/`events.*` settings at each
  import, so a change there rebuilds no plugin). A plugin whose settings hold a
  secret is registered again on every reload, so a rotated password needs only a reload.
- **Everything else** — limits, the agents' and managers' settings, media allowlists, the acquisition
  chain and TLS roots, quotas, the API key, the converter's URL — is read per request or per unit of
  work, and applies at once.
- **Restart-only**, kept at the running value and listed in the report: `server.host`, `server.port`,
  `server.request-timeout-seconds` (the listener is bound once — a second listener would buy little for
  a setting the LaunchAgent and `.mcp.json` also name), `runtime.*` (the bundled Postgres and converter
  are started once), `agents.enabled`, `agents.max-concurrent-runs`, `agents.max-llm-calls-in-flight` and
  `converter.parallelism` (pool sizes).
- **The environment** is the one read at startup: a reload re-reads the file only.

The report lists the settings applied, the restart-only ones not applied, the components rebuilt, the
plugins registered again, what is still draining, and any error; the CLI exits 2 when nothing was
applied because of an error. With `config.watch = true` the server reloads by itself
`config.watch-debounce-ms` after the file last changed (off by default; on macOS the JDK's file watcher
polls, so a change can take a few seconds to be seen).

## Blocking more hosts

The landing-page step of the acquisition chain (`oa-landing`) never reads a page from a host in
`acquire.landing.deny-hosts`, nor a PDF such a page names: the shipped list names publishers and
sites that are not repositories.
To block further sites, list them in `deny-hosts-extra`, which is **added** to that list. Setting
`deny-hosts` itself replaces the whole list, so the shipped publishers would no longer be denied:

```hocon
histmersion {
  # hosts this install must never fetch from (each entry also matches its subdomains)
  acquire.landing.deny-hosts-extra = "blocked.example,another.example"
}
```

Then run `histmersion config reload`. The same value can come from
`HISTMERSION_ACQUIRE_LANDING_DENY_HOSTS_EXTRA`.

| `plugins.keepassxc.yubikey` · `.yubikey-timeout-seconds` · `.ykman` | — (file only) | `null` · `30` · `ykman` | YubiKey challenge-response for the KeePassXC vault: `"<slot>[:<serial>]"` or a list tried in order, e.g. `["2:12345678", "2:87654321", "1"]` — each attempt adds `-y <slot>[:<serial>]` (with the password and/or key file, or `--no-password` for a key-only database). The installed service reads only its own environment: the LaunchAgent's `EnvironmentVariables`
(macOS) or the unit's `Environment=` lines (Linux). `just install` fills in `HISTMERSION_CORPUS_DIR`,
`HISTMERSION_ACQUIRE_CONTACT_EMAIL` and any `HISTMERSION_AGENTS_*` it finds in its environment; add any
other key there and `just restart`. On macOS a re-install **keeps** every `HISTMERSION_*` entry (and
`ANTHROPIC_API_KEY`/`OPENAI_API_KEY`) of the installed plist, with the installer's environment
overriding it, resolves `claude`/`codex`/`opencode` to absolute paths from its own `PATH` when no
`HISTMERSION_AGENTS_*_COMMAND` names them (a LaunchAgent's `PATH` lacks `/opt/homebrew/bin`), and
prints what it kept, set, changed and dropped, with secret values masked. To drop a kept setting:
`plutil -remove EnvironmentVariables.<NAME> ~/Library/LaunchAgents/com.histmersion.server.plist`
before installing. A `.env` in the
repo (copy [`.env.example`](https://github.com/histmersion/histmersion/blob/master/.env.example)) is read by `just` only — the recipes and the install
scripts they run.
